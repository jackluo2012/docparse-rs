# devlog · docparse-html 正文抽取（Phase 32）

> 计划：[plans/2026-09-07-html-main-content.md](../plans/2026-09-07-html-main-content.md)。2026-09-07。

## 背景与方案

消费方 shortmind-os 用 link 上传微信公众号文章，切片含模板噪声（引导关注、评论区）与句中切断。市面标杆（Readability/trafilatura/Jina）的共同三层：正文区域识别、站点专项规则、渲染兜底。本次落地前两层（渲染属"纯 Rust 快路径"身份约束外），详见计划。

## 关键实施

1. **两层抽取**：站点规则链（js_content 优先）命中即用；否则 Readability 简化打分（类名极性 + 段落质量 + 链接密度），候选 ≥25% 文本份额才采纳；都不行回退全文档——把失败模式设计成"维持现状"而非"丢正文"。
2. **模板行过滤**：平台固定文案（点击上方…关注/长按识别二维码…）整段匹配才丢，且限 60 字符内——长正文提及字样不受影响。初版手写 regex walker，方向错误（KISS），发现 regex 已在依赖树后直接用 crate（零新增供应链面）。
3. **`<br>` 语义**：collect_text 遇 br 插换行——微信作者的 br 分段是写作意图，保留为块边界。

## 踩坑与校准

- 阈值两轮校准：首轮 100/200 字符在真实短文与 fixture 上都过严——站点规则的门槛是防"JS 空壳"（静态抓取时 js_content 近空），不是罚短文章，降到 50/100。
- ego_tree 的 `tree.get(id)` 返回 `Option`（NodeId 失效安全），三处 `and_then` 链适配。
- **最重要的认知修正**：真实验收时发现引导语清除后仍剩"缘分难求"开场白与文末留言引用——它们是**作者写进正文容器的内容**。容器级/规则级清洗到此为止是正确边界；删它们需要 LLM 理解作者意图（Jina 的 LLM 模式才做），按项目"不静默吞数据"原则保留。诚实边界比"看起来全干净"重要。

## 验证

- 真实微信文章（3.3MB）：docparse 直解 chunks 18→8；"点击上方蓝色文字"清除 ✓；检索质量不变。
- shortmind-os 侧（协同仓库）：upload_link 主路径接 clean::extract_main_html，重传同文章端到端 ✓（引导语清、检索 0.993+、page/bbox 保持）。
- workspace 380 全绿（+3 main_content 测试）、clippy 零新增、fmt 过。
